# DocAlign 产品市场与成熟度审计

更新日期：2026-08-30

## 结论

DocAlign 不应定位为 Word/WPS 的通用替代品，也不应把“AI 写作”作为主卖点。更合适的定位是：

> 面向中文专业文档责任人的本地 DOCX 结构识别、格式合规、确定性整理与审计工具。

核心价值来自四个条件同时成立的场景：格式要求严格、原文不能被误改、文档不适合随意上传云端、
处理结果需要能够解释和复核。当前产品已经具备可信的格式执行内核和本地工作台，但距离成熟市场
产品仍缺少正式机构规则包、签名安装与升级、预览内可视差异等交付能力；单机本地批量处理和显式
跨设备规则迁移已形成首版闭环。

## 市场证据与替代方案

- [GB/T 9704-2012《党政机关公文格式》](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=F3CC9BEF482524C895FDA7A08BB4A70E)
  当前仍为现行国家标准，说明公文版式不是单纯的美观偏好，而是有明确规则的工作成果。
- 不同高校的论文规则并不统一。以
  [北京印刷学院 2025 年硕士论文规范](https://gs.bigc.edu.cn/docs/2025-09/1f20fd1dc1614ca7ba452d3f7df044d6.pdf)
  和[南开大学研究生学位论文写作规范](https://sfs.nankai.edu.cn/2025/0402/c7262a566018/pagem.htm)
  为例，页边距、页眉页脚、标题、正文和页码要求都有机构差异，通用“论文美化”不能等价于合规。
- Microsoft Word 已提供样式、模板、比较与修订能力；
  [标题样式会直接影响导航和目录](https://support.microsoft.com/zh-cn/word/add-a-heading-in-a-word-document)，
  [桌面版与 Web 版的格式和比较能力也不同](https://support.microsoft.com/zh-cn/word/word-features-comparison-word-for-the-web-vs-desktop)。
  DocAlign 必须提供跨段落的自动结构恢复、规则验证和审计，才能形成差异化，而不是重复字体按钮。
- WPS 已公开提供 AI 办公能力，并在 2026 年产品说明中包含
  [识别标题并应用样式](https://www.wps.cn/article/wps-wps-ai-2026-6rNYsklY.html)。DocAlign 的竞争
  重点应是本地、确定性、复杂 DOCX 安全、机构规则和可审计性，而不是笼统宣称“智能排版”。
- [《个人信息保护法》](https://www.npc.gov.cn/WZWSREL25wYy9jMi9jMzA4MzQvMjAyMTA4L3QyMDIxMDgyMF8zMTMwODguaHRtbD9yZWY9aW1i)
  将存储、使用、加工和传输都纳入个人信息处理。DocAlign 的本地优先和最小发送范围对简历、合同、
  人事材料和内部报告有实际价值，但产品文案不得把本地运行直接表述成法律合规认证。

## 目标用户

### 第一目标：机构文档责任人

典型用户包括机关、事业单位、学校、医院、国企和中小企业中的行政、综合办、秘书、项目运营、
文档专员与模板维护者。他们经常接收来源复杂、样式混乱的通知、报告、会议纪要和操作手册，最终
需要交付一份格式统一且不能改错内容的 DOCX，并把核对过的规则安全交给另一台离线电脑继续使用。

成功标准：在几分钟内理解文档结构、确认少量低置信度段落、选择机构或场景规则、得到原文安全且
可解释的输出，并能保存审计记录。

### 第二目标：论文与研究材料作者

典型用户是本科生、研究生、科研助理和教务支持人员。他们的核心需求不是“看起来像论文”，而是
满足某一学校、院系或期刊的具体规则，并能够重复检查修改后的版本。

成功标准：规则来源明确，封面、摘要、目录、各级标题、图表题、参考文献、页眉页脚和分节页码均
能被独立检查；不支持的要求必须显式列出。

### 第三目标：隐私敏感的专业职能

包括法务、财务、人力资源、咨询顾问和投标文件制作人员。他们处理合同、财务宽表、简历、方案和
客户材料，重视本地处理、表格与分节保护、变更可追溯以及批量一致性。

成功标准：不破坏合同条款、表格合并、字段、批注和附件关系；可以复用组织规则并批量验收。

### 第四目标：文档自动化开发团队

需要 CLI/API、版本化 schema、稳定定位符、幂等执行和机器可读审计。此类用户不是工作台的主要
设计对象，但可以成为集成与规模化交付渠道。

## 第一轮场景模拟

2026-08-28 使用内置合成语料和本地工作台进行模拟：

| 场景 | 分析结果 | 推荐结果 | 主要摩擦 |
| --- | --- | --- | --- |
| 行政人员整理政府通知 | 13 段，2 段待确认 | 常规文档 | 待确认项原先分散在长列表中 |
| 研究生整理学术论文 | 16 段，2 段待确认 | 常规文档 | 通用方案不能代表学校专属规范 |
| 财务人员整理宽表报告 | 6 段，1 段待确认 | 宽表优先 | 两个空段不再误计为待确认；横版推荐正确 |

八领域当前回归结果：8/8 输出通过验证，8/8 内容保护通过，所有测试污染项被清除。学术论文因
自动把一个带手动换行的正文拆为两个真实段落，源输出的“精确指纹”不同，但逻辑内容与受保护
对象保持一致；回归报告已把“内容保护通过”和“精确指纹相同”拆成两个指标，避免误报。

本机 2,000 段合成文档核心处理耗时为 3.393 秒，低于当前 30 秒质量门。该数据只代表本次本机
测量，不能替代不同硬件、图片大小、复杂表格和超大文档的性能测试。

## 第二轮结果解释闭环

2026-08-28 完成“输出生成—理解结果—回到人工复核”的闭环：

- 任务 API 增加正式 `JobResponse` 与 `JobResultSummary` 契约，不再以任意 JSON 对象表达任务结果。
- 完成页和独立任务页同时展示格式验证、原文与受保护结构校验、实际调整数量、规则动作数量、
  改动类别、执行提醒和剩余人工复核项。
- 改动按页面版式、标题与段落、文字与字体、表格、页眉页脚、视觉清理和结构重排分类，普通用户
  不必先阅读原始审计 JSON。
- 从结果摘要可以直接进入“仅看待确认”模式；财务宽表模拟中准确聚焦到唯一真实待确认段落，
  两个空段没有重新进入审核列表。
- 刷新恢复、独立任务页、短屏高级规则滚动和完整排版流程均纳入端到端回归。

## 第三轮规则包可信度

2026-08-29 对照国家标准、高校论文规范和 Word 样式体系后，完成规则包信任层：

- 四个内置方案由松散字典升级为严格的 `CleanupPresetCatalogItem`，元数据包含规则包版本、声明
  级别、适用范围、维护方、复核日期、来源引用、能力覆盖和限制。
- 当前方案统一标记为 `generic`，界面明确显示“通用方案 · 非机构合规”，避免把通用美化误解为
  GB/T 9704、学校、期刊或组织规则的完整合规。
- 用户切换常规、紧凑、合同或宽表方案时，会同步看到对应限制；例如合同方案明确不做法律审查，
  宽表方案明确不验证会计准则、金额或公式。
- `/api/v1/presets` 使用正式 OpenAPI 响应模型，来源、覆盖和限制均为必返回字段，可供未来机构
  规则包目录、审批和版本冻结复用。

这一步解决的是“可信表达”，不是正式规则包本身。现有方案仍不能对外宣称已完整符合任何国家、
高校或组织规范。

## 第四轮样例规则迁移闭环

2026-08-29 完成“合格 Word 样例—保守候选规则—人工确认”的首版模板迁移：

- 右侧新增“参考样例提取”模式，参考 DOCX 与当前待处理文档相互独立，不会替换工作区源文件。
- 参考文件经过与普通上传相同的大小、压缩包和安全校验，但只在临时目录解析；返回候选后立即
  清理，不写入文档数据库。
- 只自动采用各分节一致的页面参数，以及能稳定映射到正文、主副标题和一至四级标题等语义角色的
  已使用段落样式；候选默认关闭正文自动拆分。
- 表格示例、多级编号、页眉页脚、冲突样式、主题字体和未显式声明的继承属性只作为待确认或未覆盖
  内容展示，不会被盲目推广到目标文档。
- 候选摘要展示来源文件指纹、映射角色、纳入属性、覆盖率、歧义和未自动复制项。只有用户点击
  “确认采用候选规则”后，候选才进入当前高级规则。
- 真实页面测试确认：采用前后当前财务文档保持不变；短桌面使用右栏独立滚动，移动端使用整页
  滚动，高级规则始终可访问。

这一步满足了单次迁移与人工确认，但仍缺少候选规则的命名、版本化保存、来源审批、签名、导出和
跨工作区规则包管理，不能把一次样例提取直接表述为机构模板认证。

## 第五轮定位级结果差异

2026-08-29 完成“结果摘要—具体改动—原文位置”的首版解释闭环：

- `JobResultSummary` 增加严格的定位级差异契约，包含类别、属性路径、位置编号和格式化前后值；
  任务轮询不再需要前端下载并解析完整审计 JSON。
- 为避免大文档拖慢完成页或增加断连风险，差异先去重、优先保留有 locator 的项目，并最多返回
  32 项；页面明确提示截断，完整 mutation 始终保留在 `audit.json`。
- 页面尺寸和页边距从内部 twips 转换为毫米，字体状态转换为中文字体、西文字体、字号、粗体、
  斜体和下划线等可读字段，全局视觉清理显示发现和清除数量。
- 工作台中的段落、文字 run、表格和表格内部 locator 可以点击，自动返回文档结构并高亮对应的
  顶层段落或表格；分节和全文级变化保持只读位置标签。
- 独立任务页同样展示具体改动；人工审计 Markdown 新增最多 50 项实际变更，超出部分引导用户
  查看完整 JSON。
- 使用财务宽表真实任务验证了 44 项调整、32 项轻量摘要、毫米制页面差异、字体前后值，以及
  `p1.r1 → p1` 的结构定位高亮。

当前差异是确定性的属性级解释，不是 Word 像素级红线比较。下一阶段仍需把 locator 与中间文档
预览联动，提供源文件/输出文件的并排或叠加视图。

## 第六轮本地规则包版本库

2026-08-29 完成“准备规则—跨文档保存—版本复用—安全恢复”的首版组织复用闭环：

- 新增独立于文档生命周期的本地规则包与修订表；删除单份工作区文档不会误删可复用规则包。
- 每个修订不可变，记录适用范围、变更说明、来源类型、本地核对状态、核对说明、创建时间和规则
  SHA-256；读取与导出前重新校验摘要，损坏或篡改时阻止载入。
- “本地已确认”必须填写核对说明，界面明确说明它不等于机构认证、盖章或法规合规；从旧版恢复
  时只创建新的草稿修订，原历史保持不变且需要重新确认。
- 规则包可以载入当前文档、选择历史修订、导出版本化 `rule-pack.v1` JSON，并把当前高级规则保存
  为所选规则包的新修订。
- 所有创建、保存新修订和恢复写操作使用幂等请求标识。连接在服务写入后中断时，同内容重试返回
  原结果；同一标识被用于不同内容则明确拒绝，避免重连产生重复版本。
- 新增旧版数据库迁移测试，证明已有 `0001` 工作区能升级到规则包库；API、前端和完整性失败路径
  均有自动化回归。
- 真实旧数据模拟发现仅依赖 `create_all()` 不会补列，现已改为 API 启动前自动升级其实际数据库
  连接；升级完成后才对外服务，避免把表结构落后误判为重连失败。

这一步使 DocAlign 从一次性排版工具向可重复的机构工作流前进，但规则包仍是单机本地资产。跨机
导入、签名、正式审批人身份、组织策略锁定和可信发布渠道仍属于后续企业交付能力。

## 第七轮可恢复批量处理

2026-08-29 完成“锁定规则—提交多文档—逐文件隔离—失败重试—批次交付”的首版批量闭环：

- 新增 `batch → item → attempt` 持久化模型。批次记录规则包精确修订和 SHA-256，文件项记录当前任务，
  每次重试追加历史而不覆盖旧任务。
- 创建批次使用稳定请求标识和文件清单校验；相同请求可安全重放，不同输入复用标识会被明确拒绝。
  队列同时对活动任务去重，避免网络丢包造成重复执行。
- 文件逐个完成上传、安全校验、确定性分析和任务创建。损坏文件只标记自身失败，其他文件继续；
  上传成功后的分析或服务重启失败可以复用源文件重试。
- 批次状态由文件/任务实时推导，API 重启后已有活动任务会变为 `JOB_INTERRUPTED`，页面恢复同一批次
  并允许追加尝试。重试准备阶段也先持久化预约，异常与历史不会丢失。
- 新增版本化 `batch-audit.v1`、逐文件验证摘要、单项下载和成功输出 ZIP；ZIP 始终附带批次审计，
  不会因为一个失败文件拒绝交付已经验证通过的输出。
- 新批量页面锁定规则版本、标记草稿风险、保存批次与待确认重试请求，并用超时、取消和指数退避
  恢复轮询。组件测试验证刷新恢复和响应丢失时复用同一重试请求。
- API 测试覆盖部分失败、幂等重放、重试历史、准备阶段失败、审计和 ZIP；数据库迁移从旧版工作区
  自动升级到批次表。

这一轮覆盖的是单机人工发起批次，不是企业调度平台。文件夹监控、并发资源配额、自动保留策略、
组织审批和跨机分发仍需后续工程与真实客户验证。

## 第八轮批次生命周期与隐私收口

2026-08-29 补齐误操作控制和本地敏感材料清理闭环：

- 新增批次级幂等取消。排队任务立即进入 `canceled`，运行任务进入 `canceling`，完成当前不可中断的
  OOXML 安全阶段后不发布结果，并精确清理可能已生成的作业目录和输出。
- 批次审计升级为 `batch-audit.v2`，保留原 v1 JSON Schema 快照；新版本显式增加取消中、已取消状态
  与取消计数，避免旧消费者把新状态当成未知的普通失败。
- 批次状态与逐文件审计新增取消计数；取消中的页面继续持久轮询，断连或服务重启后取消请求仍会
  收敛为终态，不会变成可误导用户的普通失败。
- 已完成文件不受后续批次取消影响，仍可逐项下载或打入 ZIP；取消项不可重试，避免用户无意恢复
  已明确停止的工作。
- 新增终态批次删除。活动批次必须先安全停止；确认后删除批次独占的源文件、分析、规格、全部尝试
  作业、输出和审计，复用的规则包修订保持不变。
- 自动化模拟单并发下“一项完成、一项运行、一项排队”的真实取消竞争，验证完成输出保留、运行中
  输出被丢弃、排队项从未进入处理、重复取消稳定，以及数据库和文件系统删除后均无批次残留。

这使单机批次具备基本生命周期治理，但还不是自动数据保留系统。按日期/容量清理、删除失败恢复、
存储配额告警和大批量压力边界仍需继续验证。

## 第九轮本地存储治理

2026-08-29 将“资料实际保存在哪里、占了多少、删除会影响什么”从隐含实现变成可检查的产品能力：

- 新增版本化 `workspace-storage.v1` 清单，按源 DOCX、分析、任务审计、输出、批次包、数据库和其他
  文件分类统计，同时返回 DocAlign 占用、可回收候选量、本机磁盘余量与压力级别。
- 设置页新增本地存储中心，明确展示记录数量、已结束批次和未归入批次的独立文档。候选项按占用
  从大到小排列，逐项说明文件数、任务数或成功/失败情况，删除前必须确认。
- 独立文档删除增加服务端活动任务保护，不能通过绕过前端按钮删除处理中源文件；终态批次删除继续
  精确保留共享规则包。
- 默认不启用“按时间自动删除”。这是有意的保守边界：机构保存期限差异很大，应先让用户看见分类、
  对象和影响，再引入可审计的保留策略，而不是把本地优先误解为可以静默清理。
- 清单只返回逻辑名称与聚合大小，不返回正文或完整本地路径；文件扫描不跟随符号链接，避免越过
  `DOCALIGN_DATA_DIR` 统计或暴露外部文件。
- 集成测试覆盖活动任务删除冲突、任务结束后可清理、批次候选、规则包保留、项目上限和符号链接
  边界；前端测试覆盖分类呈现、确认删除、恢复记录清理和处理中按钮禁用。

这一轮采用“分类可见 + 显式确认 + 默认保留”的基线，参考了
[Microsoft Purview 的保留与删除策略语义](https://learn.microsoft.com/en-us/purview/retention)、
[macOS 的分类存储检查与用户发起清理方式](https://support.apple.com/guide/mac-help/find-and-delete-files-on-your-mac-syspf5a64aa6/mac)
和 [OWASP 对日志保留、敏感内容与安全处置的建议](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)。
当前仍不是企业保留系统：尚无按记录类型配置期限、合规锁定、清理计划预演、删除失败重试与组织
审批；大工作区的增量统计和压力边界也需要继续验证。

## 第十轮可支持性与隐私安全诊断

2026-08-29 针对行政、教务、论文作者等非开发者用户模拟“页面能打开但保存失败”和“网站完全起不来”
两条故障路径，补齐首版可支持性闭环：

- 新增版本化 `support-diagnostic.v1`，应用内检查数据库连接、迁移版本、数据目录权限、磁盘压力和
  数据库记录所引用的本地产物是否存在，并把结果分为“诊断正常 / 建议关注 / 需要处理”。
- 每项检查提供普通用户可执行的处理建议；错误历史只按近 30 天安全错误代码聚合，不返回异常原文。
- 设置页由用户主动运行诊断，并提供显式下载；报告留在本机，不存在后台上传或遥测路径。界面先
  说明采集范围，要求用户自行检查 JSON 后再决定是否分享。
- 增加离线 `python -m scripts.diagnose` 入口。API 无法启动时仍能检查环境；缺失工作区不会因诊断
  被创建，旧数据库也不会被诊断命令自动迁移或改写。
- 诊断契约明确排除正文、文件名、记录 ID、完整路径、数据库连接串、模型端点、凭据和原始日志；
  自动化用带私人姓名的文件名、伪密钥和恶意错误代码证明这些值不会进入报告。

这一设计吸收了 [Docker Desktop 同时提供应用内与命令行诊断的支持路径](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/)，
但 DocAlign 当前只生成可本地审阅的文件，不提供上传动作；字段最小化和排除清单遵循
[OWASP 对密码、令牌、数据库连接串、路径和敏感个人数据的日志建议](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)。
这已解决“统一诊断入口”和安全支持摘要。下一轮分发基础继续解决了固定项目路径和开发运行时依赖，
尚未解决正式安装器、自动更新、签名发布、可选择加入且经过清洗的启动日志，以及跨平台安装失败遥测。

## 第十一轮桌面分发基础

2026-08-29 以普通行政人员或论文作者“下载、解压、双击、开始处理”的路径复核交付能力，完成：

- Next.js 工作台改为全静态导出；原动态任务路径改用静态 `/jobs?jobId=...`，保留刷新和断连恢复。
- FastAPI 在所有 API 路由注册完成后托管静态网站，生产环境使用同源 `/api/v1`，不再需要分别启动
  Node 前端和 Python 后端。
- 桌面启动器使用系统标准用户数据目录，持有单实例锁；重复启动会打开现有工作台，端口占用时会
  自动选择另一本机端口。运行地址仍限定为 `127.0.0.1`。
- PyInstaller one-folder 产物包含解释器、依赖、Alembic 迁移和网站；隔离自检会验证静态资源与从零
  升级到最新数据库 revision，且不触碰用户数据。
- 新增 macOS/Windows 分系统 GitHub Actions 构建、产物自检和 ZIP 上传；明确记录未签名、公证、
  自动更新和真实机器验收边界，避免把测试产物误称为正式发行版。

选择静态网站加本地 API，是为了沿用已验证的浏览器工作流，并去掉终端和双服务认知负担；选择
one-folder 是为了让首版依赖与启动问题可检查。PyInstaller 官方说明产物包含解释器但不是跨平台
编译器，因此两个目标系统分别构建，不能用单一 macOS 构建冒充 Windows 验证。

## 第十二轮桌面生命周期与安全退出

2026-08-30 模拟非技术用户“关闭浏览器后为什么应用还在运行”和“任务进行中怎样退出”的场景，发现
桌面分发版缺少可见退出入口，只能依赖活动监视器或任务管理器。现已补齐：

- `/api/v1/capabilities` 明确区分开发 API 与桌面应用；设置页只在桌面模式显示“安全退出应用”，并
  解释关闭浏览器只隐藏界面，不会停止后台任务。
- 退出使用独立 POST 动作，必须带 `X-DocAlign-Action: quit`，同时拒绝跨站 `Sec-Fetch-Site` 和
  不匹配的 `Origin`；普通跨站表单无法设置动作头，跨站脚本预检也不在 CORS 允许头中。
- 桌面启动器由简化的 `uvicorn.run()` 改为 Uvicorn 官方 `Config`/`Server` 生命周期控制；响应完成后
  设置 `should_exit`，FastAPI lifespan 会等待任务安全收尾、关闭作业队列，再释放数据库、运行元数据
  和单实例锁。
- 开发服务调用退出接口返回 404，不会让浏览器页面意外关闭工程师的独立 API；缺少动作头或跨站
  请求返回 403，并有自动化覆盖。
- 分发冒烟不再通过强制终止证明“能关掉”，而是调用与设置页相同的受限接口，等待进程以状态 0
  自行结束，并验证 `runtime.json` 已删除。

该实现采用 [Uvicorn 官方的 `Config` 与 `Server` 程序化生命周期方式](https://www.uvicorn.org/#config-and-server-instances)；
[官方发行说明](https://www.uvicorn.org/release-notes/)也明确 `should_exit` 会进入 lifespan shutdown，
而不是跳过应用清理。仍需继续验证
长任务退出等待提示、系统睡眠/注销和强制关机等操作系统级边界。

## 第十三轮跨设备规则迁移与测试隔离

2026-08-30 以行政模板维护者“在离线电脑 A 核对规则，再交给电脑 B 使用”的路径复核，发现已有
导出只能完成半条迁移链路。现已补齐：

- 新增只读导入检查与明确确认两阶段流程。只接受 `.json`，默认上限 2 MB，使用严格
  `rule-pack.v1` 模型和内嵌规则 SHA-256 校验；检查不写数据库，损坏、篡改、超限和错误类型均有
  独立错误。边界参考 [OWASP 文件上传安全建议](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。
- 同名规则不会被覆盖，界面提供可编辑的无冲突名称；同一完整工件在本机或此前导入过时会定位到
  现有修订，不创建副本。写入使用稳定请求标识，响应丢失后同内容重试返回原结果。
- 目标端只建立新的修订 1，并记录来源包、来源修订、规则摘要、来源核对状态和归一化工件摘要；
  再次导出时继续携带这条直接来源记录；追溯数据结构无效或并存摘要字段不一致时会阻止读取。
- 来源端“本地已确认”不会跨设备继承。当前工件只有内容完整性摘要，没有发布者公钥签名，因此
  目标端固定为草稿，用户需重新核对后再载入。NIST 对数字签名的定义包含签署者认证与未授权修改
  检测，单独 SHA-256 不能证明发布身份，参见 [FIPS 186-5](https://csrc.nist.gov/pubs/fips/186-5/final)。
- 当前归一化摘要用于本产品去重和追溯，不宣称符合 JSON Canonicalization Scheme；未来若引入跨实现
  签名，应按 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html) 等明确规范固定序列化和签名载荷。
- 桌面与 390 px 移动视口均完成真实文件选择和导入预览。模拟发现移动工具栏把页面撑到 548 px，
  已改为两列自适应布局，并把“页面无横向溢出”加入端到端门槛；浏览器控制台无错误或警告。
- 审计还发现原端到端测试可能复用开发服务并写入日常数据库。测试现改为独立端口、临时数据目录、
  同源生产静态网站，结束后自动清理；实测既有规则记录数量前后保持 `7 → 7`。此前已有的测试命名
  记录未被自动删除，因为测试不应擅自清理既有用户工作区数据。

这一轮完成的是用户主动发起、单修订、无签名的迁移，不是云同步、完整历史备份或可信组织发布。
正式市场交付仍需数字签名、审批身份、密钥生命周期、撤销机制、组织版本冻结和全历史迁移策略。

## 成熟产品验收门槛

- **安全性**：所有输出必须通过内容、结构、受保护部件和格式验证；失败不得发布。
- **场景覆盖**：每个对外宣称支持的规则包必须有来源、版本和独立验收语料，不能用通用方案代替。
- **可用性**：首次用户能在 5 分钟内完成上传、分析、复核、规则选择、输出和结果理解。
- **可靠性**：刷新、短暂断连和 API 重启不会重复提交任务；状态恢复和失败重试必须有端到端测试。
- **性能**：建立小、中、大和极端复杂文档分层基准，不以单一段落数代表全部性能。
- **交付**：至少提供 macOS 与 Windows 的可重复安装、升级、卸载和诊断流程。
- **透明度**：明确区分“格式已执行”“内容已保护”“规则完全覆盖”和“仍需人工确认”。

以上门槛全部有自动化或人工验收证据之前，产品应继续标记为本地预览版，而不是宣称已经达到
完整机构合规或企业级成熟度。
